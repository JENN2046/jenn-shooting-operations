# Schema11 empty initialization — local candidate, not production authorization

This candidate extends the existing maintenance transaction/helper, projection refresh, initialization receipt and audit path. It does not add a startup bypass or infer revisions from an observed database. The core changes have been extracted onto default-base commit `7328bc2a7cfa17f125cba79e6fb53a08ad89e734`; PR63 is not an ancestor or runtime dependency of this branch. Existing generic offline maintenance infrastructure was already on that base. No PR63 R2/D2 files or npm check steps were imported.

## Exact supported operation

The existing packet shape remains version 1. The existing `EMPTY_DB_MAINTENANCE_SCHEMA_DIGEST_V1` still binds only migrations 1–10; a new `EMPTY_DB_MAINTENANCE_SCHEMA11_DIGEST_V1` binds exactly migrations 1–11 (version/name/checksum). Schema10 packets cannot open Schema11 as an approved target. Unknown digests or a schema that does not match the chosen prefix fail before changes.

Schema11 accepts **initialize only**. It does not admit the legacy maintenance configuration packets; after properly initializing controls and separately completing startup acceptance, resource registration/calendar preview/publish/activate use existing scoped business management APIs. This avoids introducing a second calendar configuration path or copying the default calendar into production.

The existing local synthetic runner and protected offline adapter both use this shared transaction. The local runner remains restricted to its synthetic `/tmp/jso-empty-maintenance-*` target and cannot authorize production. The offline adapter still requires its exact packet, protected policy/approval, actual runtime/target observations, writer exclusion and commit permit. No new approval or packet is generated by this change, and no host permissions/fence/configuration are applied.

## Empty means verified, not inferred

For a first initialization the implementation requires all of the following within the bound maintenance transaction:

- exact known Schema11 definitions and migration markers, SQLite integrity OK and no foreign-key violations;
- exactly one legacy schedule_state row, revision zero, with exactly the empty products/tasks/sessions snapshot;
- no rows in any other application table, including counters, audit, requests, receipts, resources, calendar, grants and reschedule history; no sqlite_sequence history;
- the existing strict storage/attachment/cleanup-fence checks, including an empty attachments staging tree, with no unknown files or ambiguous target links;
- the existing exact authorization, actor, target identity, source/image, schema digest and expected-revision bindings.

Existing business content, counters, audit or unexplained state is rejected. No data is deleted to make a database look empty. Missing markers, unknown schema objects, unreadable state or validation errors stop execution. A nonempty adoption/migration strategy is outside this candidate.

On success the existing transaction creates the zero counters, both projections, immutable initialization receipt and audit entry. It does not create resources, working calendars, identity mappings, credentials or activation permission. Transaction failure rolls these effects back. Exact replay returns the original receipt without resetting later business counters or re-projecting current data; it is not a grant to start the service or repeat initialization with new inputs.

For the rollback-journal baseline needed by PREPARED, only a journal created during the current Schema11 transaction is permitted at final target validation. A journal present at initial target validation remains uncertain state and is rejected before opening; this tool does not silently recover/delete it. WAL-mode behavior remains governed by the existing maintenance contract. The initializer does not switch journal mode. PREPARED still separately rejects a WAL baseline; any format transition requires explicit preparation/approval rather than automatic mutation.

## Breaking the initialization/startup cycle

1. Retain the current startup denial and obtain the separately bound maintenance approval; first verify the real target actually meets the complete empty-state conditions. Previous observations of missing revision/resource/calendar rows do **not** establish this.
2. Back up and validate recovery under a separately approved exclusive window before any production initialization. Execute the existing supported offline helper with a Schema11-bound packet only if every precondition holds.
3. Initialization changes the DB bytes. Preserve the pre-initialization backup, then bind the resulting baseline and its backup/restore evidence in a new prospective acceptance. The old content-hash record must not become valid merely because initialization succeeded.
4. PREPARED may then open read-only; ACTIVE still requires real Owner acceptance and trusted administrator installation. Scoped administrators can register the real resources and configure the confirmed working calendar using existing management APIs. Business identities/permissions must be explicitly configured; template values are not Owner decisions.

Local tests seed only an explicitly empty synthetic database and then invoke the supported initialization function/CLI; they do not insert the missing revision row as a substitute for initialization. Integration tests prove the pre-initialization denial, old-hash denial after initialization, newly bound PREPARED/ACTIVE and a separate-process reopen followed by another ordinary business save. They do not prove actual host permissions, production emptiness, backup restoration or offline Docker deployment.

## Production status and release scope

No new production observations, backup, initialization, deployment or configuration changes were performed for this local adjustment. Existing observations establish Schema11, absent revision row, no active resources/calendar and no core identity mapping; they do not prove all business/history tables or the legacy snapshot are empty. The prior host metadata also records the data-root mode as 0755, whereas the existing maintenance port requires a private 0700 target owned by its executing UID and a valid disabled-cleanup fence. This local change does not relax those requirements or apply permissions; the real maintenance installation/fence and any necessary permission preparation need explicit separate approval. If the real target fails the above empty checks, stop and return for a separate nonempty-data plan.

The new local image supersedes the prior `1fa7198` image only as a candidate. The old image, PR64 branch and evidence remain preserved. This local branch is not pushed and PR64 is not retargeted. A future independent PR against the verified default branch is a proposed next step, requiring explicit authorization; its new commit/image/baseline must be independently reviewed before production execution is considered.
