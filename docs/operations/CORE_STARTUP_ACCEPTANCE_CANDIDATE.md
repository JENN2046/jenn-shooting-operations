# Core Schema11 prospective acceptance — local candidate only

This implements the Owner-reviewed TRUSTED_HOST_ADMIN design. It creates no production approval and changes no historical record. Existing `RECONCILIATION_REQUIRED` and rollback `UNKNOWN` still deny startup without a separately installed complete prospective acceptance. R2 evidence approvals are not reusable business authority. No new gate, PKI, credential, SSH workflow or automatic evidence service is introduced.

## Trust and scope

A trusted host administrator must check the real Owner's identity and exact approval text through the existing trusted channel before installation. The program verifies protected material and exact bindings; it cannot establish that a human really authorized them. `approved=true` or merely creating a file is insufficient, but a trusted root can fabricate the entire record set: that remains outside this model. Historical writer/WAL coverage may be incomplete, including missing previously committed data; Owner must expressly accept that residual risk before production acceptance. No such acceptance has been generated here.

Host ID, service, host volume/mount, image digest and Git head/tree are administrator attestations of the fixed deployment, not facts discovered by the application. The program independently checks the source tree bytes, schema contract bytes, selected runtime configuration digest, canonical DB path/device/inode, Schema11 definitions/markers and required initialization rows. The administrator maintains a fixed read-only application deployment, single-writer ownership and the mount/volume correspondence. This does not prove every write's provenance or detect same-inode replacement, root tampering or rollback. Changed code/image, moved DB/volume or backup restoration needs a new exact approval, not manual editing of an old approval.

## Material contract and custody (installation is not authorized by this document)

The fixed directory is `/etc/jso/core-acceptance`, with no CLI/environment override. All its parents must be real directories owned by root and not group/world writable. Material must be regular single-link root-owned files, not group/world writable, at most 128 KiB per file. Application execution as root is rejected. Deployment must provide read access only to the service, deny application/other-user writes including through ACLs, and use a read-only mount. Apply permissions/mounts only under a later production approval. Nothing in this candidate applies them.

`acceptance.json` follows `contracts/g3-forward-reconciliation-exception.r3.schema.json`. Required fields bind:

- unique acceptance ID, purpose/version; real Owner source, original-text SHA256 and approval time; exact reviewed plan digest;
- release HEAD/tree/image and `sourceDigest()` (all `src` bytes plus this schema); host/service, volume source/name/mount, canonical DB path/device/inode, attachment root;
- Schema11 initial DB SHA256, side-file disposition, immutable historical evidence, current DB+attachments backup manifest and isolated restore verification digests;
- explicit administrator-trust/historical-risk acceptance, continuing same-target restart authorization, cleanup/integrations disabled, `runtimeConfigDigest()`; initial window and completion record.

Additional required files:

- `owner-approval.txt`: original approval text, including its reviewable channel reference; never a generated production approval.
- `owner-approval.json`: exactly `acceptanceScopeSha256`, `ownerSource`, `ownerApprovedAt`, `ownerTextSha256`. Scope is canonical acceptance excluding only `state` and `activation`. Approval covers both preparation and later ongoing operation on this exact scope.
- `plan.txt`, `historical-evidence.json`, `backup-manifest.json`, `restore-verification.json`: preserved reviewed material bytes, pinned by the acceptance. The application checks hashes, not the truth of the evidence contents; administrator review supplies that assurance.
- `installation.json`: exactly `acceptanceSha256`, `release`, `target`, `runtimeConfigSha256`, `installedBy`; binds the complete acceptance bytes and the administrator-verified deployment.
- ACTIVE also requires `initial-verification.json`, with exactly `acceptanceScopeSha256`, `baselineSha256`, `checkedAt`, `schemaVersion:11`, `integrityOk:true`, `foreignKeyViolations:0`, `backupRestoreVerified:true`, `exclusiveMaintenance:true`, `initialized:true`. `activation` binds its bytes, completion time within the approved window and installer identity. These are administrator attestations, not a claim that the application performed restoration or exclusive-writer discovery.

JSON control records use recursively key-sorted compact JSON plus one LF (`canonical`); noncanonical or duplicate-key representations fail. Digests are SHA256 lowercase hex (image digest includes `sha256:`). Evidence bytes and approval text are hashed exactly. `runtimeConfigDigest()` hashes the listed runtime settings including credential values without logging them; the material must be access-restricted and credentials high-entropy. This binds the existing business identity/resource scope and tokens; it creates no new credentials. Write-admission mode is checked separately to support PREPARED/ACTIVE. Kiosk must be disabled in the existing production context; business runtime enabled; orphan cleanup disabled.

## First acceptance, ordinary restart, and failure

1. Administrator obtains exact final approval (no TBD fields), confirms no related writers and preserves that exclusion throughout preparation/commit/start. Verify current Schema11 integrity/FKs, required initialization and consistent DB+attachments+configuration backup, including isolated restoration. Existing historical Schema10 backup is insufficient. Missing initialization is a blocker; this candidate does not seed or migrate production data.
2. PREPARED has null activation and a currently valid initial window. It checks the initial DB hash and rejects any WAL/SHM/journal. For genuinely side-effect-free SQLite reads this version additionally requires rollback-journal header bytes 1/1; WAL mode is rejected, never automatically converted. The previously observed production bytes were 1/1, but freshness must be verified before use. PREPARED uses a read-only/query-only SQLite store, no schema initialization, cleanup control writes or cleanup timer, and cannot enable writes via the existing control/SIGUSR2. An expired or incomplete PREPARED stops.
3. After read/authentication checks, administrator rechecks unchanged initial bytes under continued exclusion, records completion, and publishes complete ACTIVE material. Each file must be staged/synced/atomically renamed and directory-synced while the instance is stopped; publish `installation.json` last. A partially published set fails its digest binding rather than authorizing startup. An interrupted/uncertain install requires administrator inspection, not an automatic retry or re-creation of approval. This version provides verification and an installation specification, not an installer.
4. ACTIVE permits the specified core instance. It still checks approval, installation, source/config, target, actual Schema11 and initialization, but does not compare changing DB content against its original hash. It skips schema creation/migration and disables cleanup restoration/recovery/timers. Completing installation does not claim that the business acceptance passed. A controlled save/read/conflict/restart check is separate. First-window expiry does not revoke already completed same-target restart permission.
5. Missing/corrupt/unknown material, wrong source/config/target, schema drift or absent initialization rejects before writable open. Administrator must stop/drain the instance before revoking/removing materials; there is no live automatic revocation. After valid business writes, stop new writes and preserve the current DB/logs on failure. Never automatically overwrite with an old backup; assess lost writes and obtain a new recovery decision. Host reboot with unresolvable file/mount identity requires inspection, not path-only fallback.

## Local tests and unproven deployment boundaries

`g3-core-startup-acceptance.test.mjs` uses a disposable copy of the application with the fixed custody location and trusted UID changed only in that copy. This permits nonprivileged synthetic tests without a production override API. Every approval is labelled synthetic. It exercises server/store integration, true PREPARED read-only behavior, ACTIVE calendar publish/activate and changed-hash reopen in a separate process, rejection cases, incomplete installation, missing initialization/schema10 and window semantics. Existing business tests cover authentication/resource scope, proposal/calendar/conflict handling; a file-backed reschedule test verifies saved time and receipt after close/reopen. A process reopen is not a real container/host restart proof.

No Docker build/runtime, production backup, actual root-owned installation, reverse proxy, real authentication configuration, production initialization, snapshot restoration or production service lifecycle has been tested here. D2, Kiosk, VCP and notification delivery remain outside the candidate scope. Existing unit tests may model these components but confer no production authorization.
