# Cancel a single unstarted order/session

`POST /api/v3/business/schedule-items/:scheduleItemId/cancel` adds an authenticated administrator API for explicitly voiding a never-started order and its only session. Existing business authentication and write admission apply. The administrator must cover the registered request catalogue and the selected resource. No management-page cancellation button is added by this change.

The exact JSON command has `operationId`, `scheduleItemId`, `requestId`, `resourceId`, `expectedScheduleRevision`, `expectedProjectionRevision`, `configDigest`, `reasonCode`, and `reasonNote`. `reasonCode` must be `OWNER_CONFIRMED_NOT_STARTED`; the nonblank note records why the Owner is cancelling. The path and body session ID must agree. Obtain both revisions and the active configuration digest from the authenticated management snapshot.

The operation rejects a locked, unresolved, non-single, non-confirmed or previously executed session. It also rejects a noncanonical/closed request, a request bound to any other session, pending/retryable/leased notification delivery, mismatched scope/binding/configuration, closed admission, quiescence conflicts, and stale revisions. It requires schema12 and the existing schema3 configuration with external notifications disabled.

One transaction marks the session and its request `cancelled`, retains their IDs, planned times, buffer, attachments and task bindings, refreshes projections, invalidates stale proposals, advances both revisions once, and writes the operation receipt and audit. It creates no run event, completion fact or notification. A past plan is not treated as completed merely because its scheduled end passed. The existing dynamic-adjustment unknown-occupancy rule is unchanged; explicit cancellation removes this void session from active occupancy.

The response contains a `business.cancel.v3` receipt with the actor, before/after status, reason, revisions and `NOT_ENQUEUED_EXTERNAL_DELIVERY_DISABLED`. Query `GET /api/v3/business/operations/:operationId` to recover the original receipt. Exact replay has no new effect; changing the command or actor under the same ID is rejected. If transport fails, retain the original ID and reconcile it before deciding what to do next. Never invent an execution start/completion, delete a journal or restore an old business database to force the cancellation.

The management read model also retains resource resolution/allocation, legacy place text and note fields required by the native calendar. Tests cover HTTP auth/path binding, stale revisions/configuration, identity reuse, execution/lock/sharing constraints, atomic rollback, no notification, receipt recovery, exclusion from future proposals, and the historical-unclosed-session blocker before/after explicit cancellation.
